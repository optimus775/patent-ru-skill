# Поиск уровня техники (Step 5)

## Когда выполнять

До сборки полного комплекта документов или во время нее обязательно собрать первичный уровень техники. Выводы используются в разделах `Уровень техники`, `Раскрытие сущности изобретения`, формуле и отличительных признаках.

## Комбинированный поиск

Основной маршрут:

1. Сформировать русскую поисковую единицу для первичного широкого поиска из темы и назначения решения.
2. Найти российские документы в Google Patents через `WebSearch`.
3. Проверить широкую выдачу ФИПС через `tools/fips_search.py "<поисковая единица>" --limit 20`.
4. Для отбора ближайших аналогов запустить уточняющий ФИПС-поиск `--refine` с существенными признаками, техническим результатом, областью применения, МПК и явными исключениями.
5. Объединить результаты, убрать дубликаты и выбрать ближайшие источники.

Если ФИПС недоступен из-за сети, Browserless или изменения верстки, продолжай работу по Google Patents и другим проверяемым источникам, но явно отметь ограничение в рабочих заметках. Не используй неподтвержденные номера, даты или ссылки.

## Google Patents

Для каждой поисковой единицы используй запросы вида:

```text
site:patents.google.com/patent RU "<поисковая единица>"
```

При необходимости добавляй синонимы, английский технический термин или индекс МПК, но сохраняй фокус на RU-документах. Фиксируй только стабильные ссылки `https://patents.google.com/patent/...`, номер документа, дату публикации/приоритета, название и содержательные признаки.

Google Patents удобен для просмотра семейств, переводов и цитирования, но для российской библиографии при совпадении документа предпочитай данные ФИПС.

## Формирование поисковых единиц для ФИПС

ФИПС чувствителен к перегруженным фразам. Для `tools/fips_search.py` сначала делай 3-6 коротких русских запросов, а не одну длинную фразу:

- 2-5 ключевых слов, преимущественно русские существительные и устойчивые термины;
- без `site:`, кавычек Google, английских аббревиатур и внутренних технических слов в первом широком запросе;
- сначала родовая функция и пользовательская область, затем отдельные запросы по частным признакам;
- если выдача пустая, сразу повтори более короткий запрос, убрав аббревиатуры, прилагательные, названия протоколов, маркетинговые слова и редкие неологизмы.

Пример плохого запроса для ФИПС:

```text
радиоинформатор инвалидов по зрению BLE аудиосообщение
```

Лучше выполнить несколько отдельных запросов:

```text
информирование инвалидов по зрению
ориентирование инвалидов по зрению
радиоинформатор инвалидов по зрению
звуковая информация инвалидов по зрению
```

Английские аббревиатуры и протоколы (`BLE`, `Bluetooth`, `Wi-Fi`, `GATT`, `NFC`) используй как отдельные уточняющие признаки в `--refine` или как отдельные дополнительные запросы, но не смешивай их с длинной русской фразой в первом широком поиске.

Для `--refine` базовый query также должен оставаться широким. Частные признаки передавай через `--feature`, технический результат через `--effect`, а ложные области выдачи отсекай через `--exclude`. Если признак многозначный, например `радиомаяк`, заранее добавляй исключения для очевидных нерелевантных доменов: `самолет`, `посадк`, `глиссад`, `ВПП`, `авиац`, `парковк`, `завал`, `геолокац`, если они не относятся к текущему решению.

## ФИПС через Browserless

ФИПС запускается отдельным browser automation контуром. Перед запуском должен быть настроен `BROWSERLESS_WS_ENDPOINT` в окружении или в локальном `.env` каталога skill.

Команда:

```bash
python3 ${CLAUDE_SKILL_DIR}/tools/fips_search.py "<поисковая единица>" --limit 20
```

Уточняющий поиск для shortlist ближайших аналогов:

```bash
python3 ${CLAUDE_SKILL_DIR}/tools/fips_search.py "<поисковая единица>" \
  --refine \
  --feature "<существенный признак>" \
  --feature "<другой существенный признак>" \
  --effect "<технический результат>" \
  --domain "<область применения>" \
  --ipc "<класс МПК>" \
  --exclude "<явно нерелевантный термин>" \
  --top-k 20 \
  --details-limit 5
```

В `--refine` скрипт выполняет несколько запросов по основной области, названию, реферату, формуле и МПК, затем объединяет документы и добавляет поля `rank`, `score`, `score_reasons`, `matched_queries`. Это техническая фильтрация для просмотра человеком, а не юридический вывод о патентоспособности.

Для полного патентного поиска допускай долгий `--refine`: важнее полнота и проверяемость, чем скорость. Если нужен только быстрый контроль доступности ФИПС, ставь `--max-refine-queries 3 --details-limit 0`; если нужен глубокий медленный прогон, оставляй `--max-refine-queries 0` и при необходимости увеличивай `--details-limit`.

Разбирай строку `FIPS_HITS_JSON:` из stdout. Каждый элемент результата содержит:

| Поле | Назначение |
|---|---|
| `publication_number` | нормализованный номер публикации или патента |
| `application_number` | номер заявки, если найден |
| `title` | название документа |
| `abstract` | реферат или краткое содержание, если доступно |
| `applicant` | заявитель или правообладатель |
| `inventor` | автор, если найден |
| `publication_date` | дата публикации |
| `filing_date` | дата подачи |
| `source_url` | проверяемая ссылка на ФИПС |
| `database` | база ФИПС |
| `source_adapter` | `fips` |

Если элемент содержит `error_code`, это управляемая ошибка. Не считай ее источником уровня техники; используй сообщение для заметки о недоступности ФИПС и продолжай поиск по Google Patents.

## Дедупликация и приоритеты

Объединяй результаты:

1. по нормализованному `publication_number`;
2. затем по `application_number`;
3. затем по `source_url`;
4. затем по нормализованному названию.

Если один документ найден в ФИПС и Google Patents, в таблице можно оставить обе ссылки: ФИПС как официальный источник библиографии, Google Patents как удобную страницу семейства/перевода.

## Дополнительные источники

Используй, когда Google Patents и ФИПС недостаточны:

- Espacenet, WIPO Patentscope, USPTO, EAPO, если релевантно;
- научные публикации через DOI, издателя, arXiv или другую устойчивую страницу;
- сайты производителей и документацию только как непатентный уровень техники, если дата публикации проверяема.

## Что фиксировать

Для каждого релевантного источника:

| Поле | Требование |
|---|---|
| Идентификатор | номер публикации, патента, DOI или иной стабильный идентификатор |
| Название | как в источнике |
| Ссылка | проверяемый URL; не придумывать ссылки |
| Дата | дата публикации/приоритета, если доступна |
| Суть | краткое содержание технического решения |
| Общие признаки | что совпадает с текущим решением |
| Ограничения | почему источник не решает текущую техническую проблему полностью |
| Отличительные признаки | что должно перейти в раскрытие сущности и формулу |

## Формулирование для заявки

В разделе `Уровень техники` не нужно включать весь журнал поиска. Дай сжатый обзор ближайших источников и их недостатков. Заверши выводом, какие признаки отличают заявляемое решение и почему они связаны с техническим результатом.

## Запреты

- Не утверждать патентоспособность как установленный факт.
- Не писать в российский комплект фиктивные ссылки, даты или номера.
- Не включать в итоговый документ служебные ошибки Browserless или внутренние параметры `.env`.
